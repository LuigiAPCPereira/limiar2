## 2025-06-09 - [File Permissions] Forçar criação do banco SQLite/Tursogo com 0600
**Vulnerabilidade:** O arquivo de banco de dados (`.db`) que hospeda a sessão MTProto do Telegram e as mensagens em texto plano estava sendo criado com o umask padrão do sistema (que normalmente resulta em permissões `0644`), permitindo que outros usuários locais no mesmo sistema acessassem os dados críticos.
**Aprendizado:** A criação automática de arquivos pelo driver `database/sql` para bancos de dados baseados em arquivos pode não aplicar regras de segurança estritas, deixando os arquivos resultantes vulneráveis a leituras não autorizadas.
**Prevenção:** Antes de chamar `sql.Open(...)`, deve-se criar manualmente o arquivo do banco de dados (se não existir) utilizando `os.OpenFile` com permissões `0600` e, caso exista, aplicar `os.Chmod` para garantir que as permissões restritas (owner-only) continuam sendo aplicadas. Isso assegura que dados sensíveis armazenados localmente sejam fortemente protegidos em nível de sistema de arquivos.

## 2025-06-10 - [Log Injection] Prevenção de Log Injection e MTProto Injection via input de username
**Vulnerabilidade:** A função `NormalizeUsername` extraía substrings do username fornecido pelo usuário via CLI (ex: `channels add <username>`) mas não sanitizava o conteúdo real. Uma entrada como `@username\nAdmin` ou com parâmetros web como `?start=x` poderia causar vazamentos nos logs de stdout (Log Injection) e requisições malformadas na API do Telegram (SSRF / MTProto Injection).
**Aprendizado:** Todo input advindo do usuário, especialmente aqueles que serão enviados a APIs externas ou logados em disco/stdout, deve passar por validação estrita (allowlist de caracteres esperados). Neste caso, a regex `^[a-zA-Z0-9_]+$` protege contra payloads indesejados.
**Prevenção:** Antes de utilizar e logar variáveis como `username`, aplique sempre a sanitização rigorosa — como a remoção de control characters (`\n`, `\r`) e fallback seguro validando em loop ou regex. Além disso, identificou-se que `d.log.Error("💥 Panic no handler recuperado", "panic", r)` no Dispatcher expõe o objeto bruto do panic `r`, que no futuro deve ser mitigado.

## 2025-06-10 - [Segurança] Panic Recovery vazando dados sensíveis no log
**Vulnerabilidade:** O panic recovery no `Dispatcher` (`internal/telegram/dispatcher.go`) estava logando o objeto bruto de panic (`r`) diretamente via `d.log.Error(..., "panic", r)`. Isso poderia vazar dados altamente sensíveis da memória, como o MTProto session token ou conteúdos de mensagens, caso um erro inesperado expusesse essa variável durante o processo na goroutine.
**Aprendizado:** Logar o tipo (`%T`) perde informações de depuração essenciais. É mais apropriado envelopar a mensagem usando `fmt.Errorf("panic: %v", r)`. Assim, extrai-se a mensagem literal sem utilizar a reflexão sobre o objeto, o que previne dump de structs com segredos embutidos, ao mesmo tempo que mantém informações valiosas sobre o erro ocorrido.
**Prevenção:** Nunca logue o objeto bruto do `recover()` (`interface{}`) como valor direto em chaves de log (que utilizam reflexão). Em vez disso, converta-o para um erro com `fmt.Errorf("panic: %v", r)`.

## 2025-06-12 - [Information Leakage] Erros brutos expostos na API HTTP
**Vulnerabilidade:** A API do dashboard estava expondo erros internos detalhados (ex: `err.Error()`) nas respostas HTTP usando `http.Error()`, vazando informações sensíveis sobre o estado do sistema ou caminhos internos.
**Aprendizado:** A exposição de raw internal errors a clientes não autenticados pode facilitar a enumeração do sistema.
**Prevenção:** Sempre utilize respostas de erro genéricas como `http.StatusText` ao cliente e registre o erro original completo apenas no log interno.

## 2025-06-13 - [File Permissions] Correção de umask permissivo em bancos existentes
**Vulnerabilidade:** Embora os bancos de dados estivessem sendo criados com permissões 0600 (ou o recomendado 0o600 para Go >= 1.20), bancos de dados que já existiam, mas haviam sido criados anteriormente com o umask padrão (0644), mantinham suas permissões permissivas, expondo a base de dados SQLite/Tursogo a outros usuários locais na mesma máquina. Adicionalmente, a sintaxe legada de permissão `0600` estava sendo usada ao invés da moderna e menos sujeita a erros `0o600` recomendada para evitar warnings do gosec G306.
**Aprendizado:** Apenas usar permissões restritas em `os.OpenFile` com a flag `os.O_CREATE` afeta apenas a criação de novos arquivos. Para garantir de modo retroativo que o estado do sistema se alinhe aos requisitos de segurança, deve-se reforçar as permissões para arquivos já existentes. Além disso, Go >= 1.20 recomenda fortemente a sintaxe `0o` para octais para garantir clareza no linting.
**Prevenção:** Adicionar um fallback usando `os.Chmod(filepath, 0o600)` após o check de verificação se o arquivo existe assegura que bancos legados inseguros ou arquivos que tenham tido suas permissões modificadas externamente sejam reparados automaticamente ao inicializar o banco de dados. Utilizar também apenas a sintaxe `0o600` em todo o código gosec G306.

## 2025-06-13 - [CI Lints] Correção de regras rígidas de lint
**Vulnerabilidade:** Nenhum impacto direto de vulnerabilidade na infraestrutura, porém a detecção frequente de code smells, regras ignoradas e retornos de erros suprimidos em partes críticas do sistema (`golangci-lint`) indicam dívida técnica e podem induzir à perda de contexto em erros críticos ou vazamento de handlers (e.g. `defer rows.Close()` não validando seu errcheck).
**Aprendizado:** A conformidade com os analisadores de código estático (como o `errcheck` ou `unused`) não é apenas sobre o pipeline passar; em Golang, `Close()` em operações deferidas podem sinalizar panics de flush ou falhas no encerramento de conexões. Variáveis regex declaradas globalmente mas nunca utilizadas apenas adicionam custo de alocação de memória na inicialização do pacote.
**Prevenção:** Em casos de deferred cleanup functions cujos erros não afetem a lógica ou os nós de recuperação da stack call (e.g., `_ = f.Close()`), o retorno da função ainda assim precisa ser explicitamente negligenciado por uma função anônima para agradar os verificadores (e.g., `defer func() { _ = rows.Close() }()`). Sempre garantir que o build e vet ocorram na infra local.

## 2025-06-13 - [Tooling/Testing] Supressão segura de alertas gosec (SSRF e Tainted Input)
**Vulnerabilidade:** A ferramenta de benchmark `tools/bench-dashboard-contention/main.go` disparava avisos de segurança no GitHub Actions (gosec) devido ao uso de G704 (SSRF) nas requisições HTTP (`http.NewRequestWithContext` e `client.Do(req)`) e G204 (Subprocess with a potential tainted input) na inicialização do subprocesso via `exec.CommandContext` com variáveis controladas por configuração.
**Aprendizado:** Embora as regras de SSRF e subprocesso não seguro sejam críticas na aplicação principal (`limiar-collector`), a sua aplicação cega em ferramentas de desenvolvimento (testes, fuzzers, benchmarks) pode quebrar as pipelines de CI, mascarando falhas reais no código produtivo. Ferramentas que fazem load testing invariavelmente criam requisições HTTP dinâmicas baseadas em argumentos, o que o linter corretamente aponta como potencialmente inseguro.
**Prevenção:** Em diretórios de testes internos (`tools/`, testes), é perfeitamente válido silenciar avisos intencionais usando comentários do tipo `// #nosec GXXX`, desde que isso seja feito unicamente no escopo e linha específicos do erro para não suprimir globalmente uma classe de checagem.
