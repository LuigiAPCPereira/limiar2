## 2024-05-18 - Index SQL para paginação no Dashboard
**Aprendizado:** As queries do dashboard usam `ORDER BY received_at DESC`. O SQLite realiza um *TEMP B-TREE* para a ordenação devido a ausência de um índice em `received_at`, isso tem um alto custo para grandes volumes de dados.
**Ação:** Criar os índices `idx_raw_messages_received_at` para listagens gerais, e `idx_raw_messages_channel_received_at` para listagens otimizadas por canal otimizando a latência do dashboard.
## 2024-05-24 - Early Return no Dispatcher para Updates Ignorados
**Aprendizado:** Updates do Telegram que não contêm mensagens de canais monitorados (como updates de `UserStatus`) passavam por uma codificação JSON pesada (`json.Marshal`) no `onUpdate` antes de serem descartados (seja por falha ao extrair metadados ou por não constar na lista de canais monitorados). Isso causava consumo alto de CPU e inúmeras alocações de memória inúteis no hot path da aplicação. O JSON marshal cria alocações de buffer e onera o GC por um dado que é sempre jogado fora.
**Ação:** Incluir early returns baseados nas informações mais fáceis de obter primeiro (verificar se há canal e extrair metadata antes de rodar o `json.Marshal`). Quando aplicável, checar filtros leves (como `extractUpdateMeta`) antes de executar transformações pesadas para melhorar radicalmente a performance (de ~600ns e 1 alloc para ~8ns e 0 allocs para updates ignorados).
